# Project coordination and safe parallel-work backend

This package is the reusable server-side engine behind issue #167: an owner appoints a bounded project coordinator, the trusted result boundary hands the engine exact retained-result evidence, approved proposals become ordinary canonical work, and no two workers unsafely write the same project resources. It implements `docs/PROJECT_COORDINATION_IMPLEMENTATION_CONTRACT.md` and the strict shared boundary module `src/contracts/v1/project-coordination-boundaries.ts` without redesigning either. It is additive: it introduces no scheduler, no agent login, no second authority system, and it wires none of the existing manual, scheduled, news, retained-result or dispatch/activation call sites.

## Authority

`WebSessionAuthority` stays human-only. `ProjectCoordinatorServiceV1` appoints, replaces, re-appoints and revokes a coordinator, and every one of those operations first locks the initiating human identity and its currently valid owner grants. An agent identity cannot satisfy that check, so a coordinator cannot appoint itself, widen its own bounds, approve its own proposal or acquire a session. An appointment writes only the versioned head row in migration 0075; it creates no identity, role grant, policy decision, approval, attempt, lease or outbox entry. A revoked head row remains and its next assignment increments the same head version. A human coordinator carries no execution binding at all; an agent coordinator carries exactly one, whose digest is `sha256Digest({schema, tenantId, projectId, coordinatorIdentityId, executorId, adapterId, connectorProfileDigest})` with the schema fixed by the shared module, and whose identity ID may never equal its executor ID.

Migration 0075 reserves only `active` and `revoked` for the coordinator head, and the contract allows pause and revoke as the only in-place policy changes. Pausing a coordinator is therefore expressed as pausing its bounded delegation policy: automatic adoption stops immediately while owner-reviewed adoption of already-accepted proposals stays available. `pauseDelegation`, `resumeDelegation` and `revokeDelegation` are the owner-authorized operations for that, and a revoked policy can never be resumed.

## Proposal ingestion

`validateCoordinationProposalV1` accepts only `control-room.verified-coordination-result-evidence/v1`, the strict engine port carrying the server-created planning marker, the stable execution binding, the retained artifact identity, the immutable receipt digest, the exact content digest and the retained text. There is no browser-facing entry point and no path that turns raw transport input into a proposal; a browser-supplied agent identity is not a field the port accepts, so it fails the strict parse rather than being ignored. The marker must name exactly the presented binding, and the presented text must hash to the exact content digest recorded for the retained artifact, so a substituted or edited body cannot be parsed as a plan.

The retained text is read by `parseStrictJsonObjectV1`, a purpose-built strict reader rather than `JSON.parse`. It consumes the input as exactly one JSON object, refuses duplicate keys at any depth (which `JSON.parse` silently resolves to the last value), refuses `__proto__`, `constructor` and `prototype` keys, refuses any byte before or after the object — a code fence, an explanatory sentence or a second value — and refuses input above the 65,536-byte retained-result limit. The resulting object is then validated against `control-room.project-coordination-proposal/v1`, a strict schema limited to 32 tasks and 64 dependency edges whose fields are only a local ID, a title, instructions, a required capability and an optional recommended route. There is no field through which result content could supply authority, credentials, an endpoint, a callback, an effect, a risk or a cost, and no field through which it could name its own coordinator identity, coordinator version, owner or policy. Cyclic dependency edges are refused, because they would persist canonical jobs that can never satisfy their dependencies.

`recordProjectCoordinationProposalV1` commits the outcome under lock. It rechecks the current coordinator head — state, identity, version and execution-binding digest — and performs a verified read of the immutable native artifact receipt, so a result produced by a coordinator that has since been replaced or revoked is recorded as rejected rather than adopted. Rejections store a bounded reason code only (`content_duplicate_key`, `content_over_limit`, `proposal_cross_project`, `evidence_binding_mismatch`, `coordinator_not_current`, and the rest); the invalid text stays in the protected artifact and is never copied into a row, an error message or a log line. Re-ingesting the same run returns the stored outcome instead of writing a second proposal.

## Adoption

`ProjectCoordinationAdoptionServiceV1` first loads the exact accepted proposal row through `loadAcceptedProjectCoordinationProposalV1`, which re-derives the stored content's digest, and resolves every selected task's route and cost **from that canonical row alone**. A caller-supplied proposal object is optional and is never a routing or pricing input: when one is supplied it must hash to the exact stored proposal digest or the operation refuses with `proposal_evidence_mismatch`, so a cheaper or differently-capable copy cannot be priced and then paired with different persisted content. The resolved routes and prices travel with that proposal digest, and the canonical transaction refuses to commit them against any other proposal. Routes come from a server-side resolver and costs from a trusted cost-evidence port; both then enter one canonical operation. Owner-reviewed adoption and bounded-policy adoption differ only in which authority row the transaction locks; they produce the same non-runnable `request`/`workflow`/`job` records through the same canonical insert path, the same `control_job_dependencies` edges and the same resolved owner-attention item. Every destination job is `proposed` with `networkPolicy` `none`, no credentials, no filesystem roots, no network destinations, `effectPolicy` `none`, zero concurrent effects and zero cost, and the operation creates no attempt, lease, approval, effect intent or dispatch. A recommendation is data, not permission.

Exact replay is verified **before any mutable-current-state check and before any mutable port is consulted at all**. An operation that already committed was fully verified when it committed, so `adopt` first calls `findCommittedProjectCoordinationAdoptionV1`, which locks the receipt row for this authorization kind, initiating identity and idempotency key, requires the operation ID and the stored **request identity digest** to match exactly, recomputes the stored receipt payload's digest, confirms the canonical job rows it names still exist, and returns that original receipt with no authority, coordinator, policy, route or cost re-check and no new accounting. Only a request that has never committed reaches the route resolver or the cost-evidence port. A caller-supplied proposal copy is still cross-checked on a retry, against the proposal digest the original operation committed. A coordinator or policy revoked after the fact therefore cannot retroactively break the receipt for work that legitimately exists, while a genuinely new operation after revocation, or on a route that is no longer available, still fails closed.

For requests that are not an exact replay, the atomic order is the one the contract fixes: initiating owner identity and grants; tenant; project and manual-project head; coordinator head; policy head when one is used; the proposal row and its verified artifact receipt; referenced existing jobs in sorted ID order; then the destination jobs and the receipt. The policy row serializes quota accounting, and the replay lookup is repeated with that lock held, so a concurrent retry that queued behind a first commit reads the committed receipt rather than racing a duplicate insert.

Changed input under the same key conflicts, before and after revocation alike. Identity is `coordinationOperationRequestIdentityDigestV1` — `sha256Digest({schema, request})` over the caller's request alone — and it is recorded in the receipt payload as `requestIdentityDigest`. It deliberately excludes the routes and the price the server resolved, which the separate request digest still binds and the receipt still records: route resolution and pricing are current-state services, so a route that has since been retired or trusted cost evidence that has since moved must not make a legitimately committed receipt unreachable, and the identical committed request returns its original answer. Everything the caller controls — proposal, selection, approved routes, authorization, operation and idempotency keys, timing — is inside that identity, so genuinely changed content under one key is still `adoption_replay_conflict`, refused before anything is routed or priced. A second adoption of the same proposal under a fresh key is refused outright, matching migration 0075's one-adoption-per-proposal index.

Every automatic bound fails closed. A paused policy, a revoked policy, a policy outside its validity window, a policy whose coordinator version no longer matches the head, a route outside the policy's server-resolved eligible routes, an exhausted task allowance, an exhausted micro-USD ceiling and an exhausted concurrency allowance all refuse. Missing or unreadable cost evidence is `cost_unknown`; it can never satisfy a ceiling, including a zero ceiling, and an agent estimate is never evidence. Owner-reviewed adoption remains usable on an unpriced route and records a null admitted cost rather than a fabricated zero. Micro-USD accounting is exact `BigInt` arithmetic, because the ceiling is a bigint column and a double comparison could silently admit an over-ceiling operation.

Policy-scoped concurrency is counted as adopted, policy-linked canonical jobs that have not reached a terminal state. That is stricter than counting only active leases, because a proposed policy job also consumes its unit; the strictness is deliberate and fail-closed. A partial selection may not drop half of a dependency edge, since adopting only the dependent half would make work runnable earlier than proposed.

## Shared work admission and resource conflicts

`admitProjectWorkResourcesV1` is the single canonical resource-conflict operation. Manual, scheduled and news-collection callers differ only in `routeKind`; they share the request shape, the operation and one lock order — authority (including the standing owner policy, when one is invoked), tenant, project/schedule head, job, every immutable resource registry row sorted by resource ID, existing held admissions and scopes, node, lease and attempt, then the new holder and its scopes. Scheduled callers acquire the tenant before their project read for exactly this reason. There is no private path by which a route could acquire a holder, and no route has its own order that could deadlock against another.

Authority for admission is an authority to admit, never a bare live policy. A request whose `authority` is `kind: "owner"` locks the initiating human identity and its currently valid owner grants for the `work.admit` action. A request whose `authority` is `kind: "policy"` additionally requires the cited standing delegation policy to exist, belong to this project and this initiating owner, be `active`, be inside its validity window **and list `work.admit` in its allowed actions**. A delegation policy is a bounded grant of named actions, not a token of general standing: a policy that lists only `proposal.adopt` delegates proposal adoption and nothing else, and refuses with `policy_action_not_permitted` rather than standing behind a resource holder — least of all a whole-repository writer, the widest holder this operation can create. There is no wildcard: the exact action must be listed. That check runs at the authority step, before any other state is read and before any holder exists.

The declaration is canonicalised inside the transaction by `canonicalProjectWorkResourceDeclarationV1`, so a caller cannot present a pre-digested declaration the engine never re-derives. Resource identities and configuration digests are checked against the immutable registry; `control_work_resources` is unique on the folded comparison key, so a client cannot register a different spelling of the same repository to evade conflicts. Repository paths compare as lowercase complete segments, and the boundary's path grammar refuses traversal, absolute paths, empty segments and backslashes, so `../escape`, `/etc/passwd` and `SRC/Feature` are respectively refused, refused and folded onto the scope they actually overlap. A missing declaration refuses with `resource_declaration_missing`; it is never guessed as read-only.

Two readers share a resource. A writer conflicts with any overlapping reader or writer. A tree scope overlaps its descendants and a root tree overlaps the whole repository. A repository writer that declares anything narrower than the whole repository is admitted only when both facts are established outside the request. A request may ask for parallel narrow writing and name a policy; it cannot assert the permission and it cannot state its own workspace. The named policy is read and verified against the stored `control_project_delegation_policies` row inside the transaction, at the standing-policy step of the lock order: it must exist, belong to this project and this initiating owner, be `active`, be inside its validity window, list `work.admit.parallel-narrow-write` in its allowed actions, and cover every resource this declaration writes narrowly in its `parallelNarrowWriteResourceIds`. The workspace comes from `EnforcedWorkspacePortV1`, the trusted workspace/lease boundary captured in the server/node composition exactly as the retirement verifier is; `authorizeParallelNarrowWriteV1` resolves it for the exact tenant/project/job/attempt/lease/node/admission lineage and mints a frozen branded authorization that the canonical store will not accept in any hand-made form. The resolved workspace must be the one the declaration was actually built from, and it must differ from every holder already touching that repository. An engine composed without that boundary can never admit a narrow writer. Otherwise the declaration must take a root-tree write scope and serialize. Logical-only work uses `workspace.kind=none`, the reserved immutable anchor, `baseRevision=no-workspace:v1` and a deterministic no-workspace intent digest; the anchor is stored in the legacy-named `repository_resource_id` column and is not itself a conflict scope.

No holder is created without the exact current lineage. The job must not be terminal or still merely proposed; the lease must exist, name this job, attempt and node, be `active`, and not have expired by the acquisition instant; and the attempt must exist, belong to the same job and node and still be `leased`, `running` or `waiting`. A stale or unstarted lease that could create a holder would be unreleasable, because only authenticated process-retirement evidence releases one. Exact replay of an existing admission is unaffected, so a restarted server still sees its held holder.

Admission replay is identity, not resemblance. A stored holder replays only when every piece of lineage it was stored with is the lineage now being presented — admission, project, job, attempt, lease **and node**, together with the declaration digest, the workspace intent digest, the route kind, the enforced workspace and the parallel-write policy the holder was admitted under — and only when the admission digest recorded with the holder is the digest this request derives. The node is part of the immutable admission digest, so omitting it from the comparison would let a request naming a different, even nonexistent, node be answered `replayed: true` with a digest persistence does not hold while the real holder stayed untouched. Anything that does not match is a changed request and refuses with `resource_admission_replay_conflict`; a holder that does replay is answered from the stored row — its digests and its version — never from values re-derived from the request that asked for it.

Unknown legacy work blocks new admission — readers as well as writers — until it is reconciled, because an attempt with no admission record may hold anything and judging a declaration against it would require a guess. The check counts started attempts (`leased` with a start time, `running` or `waiting`) that have no admission row. An attempt that has not started is excluded, because the start fence refuses to release transport bytes without a current-holder proof and so such an attempt cannot already hold a resource. Started legacy work continues through its existing result path unchanged.

Every admission returns an immutable declaration digest and the separate admission digest `sha256Digest({schema, tenantId, projectId, jobId, attemptId, leaseId, nodeId, admissionId, declarationDigest})`, which binds the exact attempt lineage so one attempt cannot reuse another attempt's declaration. `recheckProjectWorkResourceAdmissionV1` re-reads the holder before a start fence and refuses when the record is absent, retired, bound to different lineage, or when the declaration has changed since admission. Live dispatch/activation binding to that digest remains pending lead integration; this package only produces the digest and the lookup.

## Retirement

Lease expiry, disconnect, browser closure, arbitrary result text and a bare transport receipt never release a resource holder, and none of them reaches the retirement code path. The only release is `control-room.process-retirement-proof/v1` bound to tenant, project, job, attempt, lease, node, admission and run, with the process and source evidence digests, checked by a verifier captured in the server/node composition rather than supplied with the request. `authorizeProcessRetirementV1` parses the proof, calls that verifier, treats a throwing or negative verifier as a refusal, and mints a frozen branded authorization; `retireProjectWorkResourceAdmissionV1` accepts nothing else, so a hand-made authorization object is rejected. The transaction recomputes the admission digest from the stored declaration and refuses a proof that does not match it, or that names a different attempt or lease. Retirement is idempotent for the exact proof and conflicts for different evidence on an already-retired holder. Quality acceptance and capacity release remain separate decisions: a finished or succeeded job still holds its resource.

The database's reserved `trusted_no_start` value has no proof contract, so this package never produces it and `refuseNoStartReleaseV1` exists to make that explicit. Absent process-retirement proof, the holder stays held.

## Acceptance data and the unrun PostgreSQL gate

`tests/project-coordination-backend.test.ts`, `tests/project-resource-admission.test.ts` and `tests/project-coordination-retirement.test.ts` use disposable in-memory PGlite data, the pattern the rest of this suite already uses for canonical-store coverage. They prove the service decisions, the exact SQL the transactions issue and the fixed lock order. They deliberately do not claim real PostgreSQL serialization: PGlite runs one embedded engine and cannot demonstrate two independently supplied connections racing under real MVCC.

`tests/project-resource-admission.test.ts` therefore carries a disabled-by-default independent-connection gate. It takes two separate `pg` pools, asserts they are distinct backends, applies the migrations and the same seed data the in-memory suite uses, builds one `CanonicalStore` per connection, creates the parent request/workflow/job/attempt/lease rows through the ordinary canonical path, and then has both stores call the real canonical admission operation `admitProjectWorkResourcesV1` concurrently for overlapping root-tree write scopes on the same repository resource. It inserts no row by hand. Exactly one call must be fulfilled; the other must be refused on the contract's own terms (`resource_conflict`, `resource_admission_replay_conflict`, or a serialization/deadlock failure PostgreSQL raised), and the durable state must end with exactly one held holder. It is skipped unless `CONTROL_ROOM_PG_CONCURRENCY_GATE=1` and both URLs are supplied:

```
CONTROL_ROOM_PG_CONCURRENCY_GATE=1 \
CONTROL_ROOM_TEST_PG_URL_A=postgres://<disposable> \
CONTROL_ROOM_TEST_PG_URL_B=postgres://<disposable> \
node --import tsx --test tests/project-resource-admission.test.ts
```

It has not been run. Provisioning a database, connecting to an external database and running this gate are not authorized by this contributor package; that run remains a parent #167 acceptance gate after the restricted database-role package (#63). No always-on external service or secret-dependent public CI job is added.

## Delegation-policy lifecycle durability

Pausing, resuming, and revoking an owner-authored bounded policy run through the same durable shape as the coordinator lifecycle, on the distinct `project-delegation-policy-lifecycle` scope of the existing `control_idempotency` safety system — no new table, no new authority. `delegationPolicyLifecycleRequestDigestV1` binds the action, tenant, project, policy, owner, and expected version; `setProjectDelegationPolicyStateDurableV1` claims the key, probes the locked receipt ledger before any version gate (an exact retry returns the recorded receipt with `replayed: true` even after the policy has moved on), then enforces the expected version (`policy_version_stale`), computes the already-state outcome when the policy already names the target **and the caller's version is current** (`policy_already_active`, `policy_already_paused`, `policy_already_revoked` — originating in PostgreSQL, never invented by the HTTP layer; only an exact saved-receipt replay may bypass the version guard), refuses changed content under a recorded key (`policy_replay_conflict`), mutates at most once per key, and writes the completed receipt carrying the new version, state, and digest. The HTTP service defers the policy version to this engine — the revision gate skips it so a retry always reaches the ledger probe — maps `policy_version_stale` to the long-standing `stale_revision` wire code with a re-read head version, and passes the already-state and conflict codes through unchanged. The private UI still offers no policy buttons (unchanged from #200); the routes now serve them through the durable path instead of refusing. Covered table-driven in `tests/project-coordination-backend.test.ts` (pause/resume/revoke × first execution, exact retry, changed content, rebuilt key, restart-rebuild, already-state, simultaneous duplicates), `tests/project-coordination-http.test.ts` (already-state mapping, replay-before-stale, stale envelope), `tests/coordination-route.test.ts` (route flow with the exact key and revision, facade invocation proof), and `tests/postgres-production-coordination.test.mjs` (the same lifecycle against a live PostgreSQL 17 cluster: one mutation, saved receipt, conflict, stale, single completed ledger row).
