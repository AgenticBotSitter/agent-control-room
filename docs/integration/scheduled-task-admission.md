# Scheduled task admission

The scheduled-task admission service maps one already-materialized, exact schedule occurrence to one canonical request, workflow, and job in their non-runnable proposal states. The durable receipt is keyed by tenant, schedule, and occurrence. Its destination identifiers are derived only from that occurrence's tenant, schedule identifier, occurrence key, current schedule-definition digest, and exact source-bundle digest.

Admission binds the canonical tenant/workspace/project/schedule, the current active schedule definition, the occurrence, and the exact source request/workflow/job bundle. Version one accepts only a job target. Its reusable-context binding is explicit and digest-bound: empty is a real choice, while every non-empty entry carries immutable result/artifact, content-hash, source job/run/revision, review and verification lineage. Admission records that claim but does not prove the referenced context is current; the scheduled planner verifies it and the assignment transaction verifies it again. A changed definition, source bundle, context binding, or locator refuses rather than creating another proposal. An expired recovery window also refuses before any write.

The destination job remains `proposed`. It has an unassigned executor, no credentials, filesystem roots, network destinations, effects, cost, assignment, or retry permission. The receipt's `startsWork`, `grantsExecutionAuthority`, `permitsAssignment`, `permitsRetry`, and `permitsCancellation` fields are all permanently false. The receipt does not prove a task ran, succeeded, or was reviewed.

Exact concurrent or restarted admission returns the same immutable receipt. The canonical proposal and receipt commit in one transaction. Occurrence delivery acknowledgement happens afterwards through `ScheduleOccurrenceStore.acknowledgeDelivery`; therefore a process loss between commit and acknowledgement is recovered by replaying the receipt and acknowledging the existing occurrence. `dispatched` continues to mean only that occurrence delivery was recorded.

Pause blocks new admission but does not cancel a receipt that already exists. Resuming within the original recovery window permits admission. Pending occurrence cancellation and admission serialize on the same occurrence lock: cancellation first marks only the occurrence cancelled; admission first makes later occurrence cancellation refuse.

The separate scheduled-assignment service consumes this receipt only under an owner-created standing policy bound to the same tenant, workspace, project, schedule definition, source bundle and context policy. The owner identity must still be active and retain a current owner-role `tasks.assign` grant for that project; suspension, grant loss, pause, revocation, expiry, policy drift or context drift blocks the next boundary. Non-empty context is resolved through the authenticated native-or-Codex result receipt and checkpoint-authenticated completion target, accepted reviews, required passing verifications and revision lineage. Those exact references are included in the canonical plan input and its digest, then resolved again inside assignment. Policy and context time fences run once more immediately before commit.

Planning and assignment have separate immutable replay boundaries, use the ordinary canonical planner and the same locked capacity allocator as owner assignment, and audit actions as `service:schedule-assignment:v1` while retaining owner policy identity and digest lineage. Both operations lock the stable policy row before checking for an absent receipt, so PostgreSQL callers serialize and a waiter reads the committed receipt instead of racing a duplicate primary-key insert. The disposable PGlite suite verifies concurrent replay and the required SQL lock ordering, but PGlite does not reproduce independent-connection PostgreSQL MVCC; integration should retain a real-PostgreSQL concurrency gate when the restricted #63 role package is composed. A committed lease is evidence only of retained capacity: no receipt starts a process, grants execution authority, claims native cancellation or releases capacity. Queueing, transmission, providers, credentials, native cancellation and production scheduling remain outside both services.
