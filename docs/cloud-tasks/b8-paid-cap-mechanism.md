## What the specification must cover

1. **Inspect before designing.** Trace `src/usage/v1/usage-cost.ts`, its tests, `src/web/v1/improve-control-room-loop-adapter.ts`, the loop service and relevant public harness execution seams. The existing usage-cost module prices reported usage after execution; it does not reserve a cap before a call. Name real callers and explicitly mark NEW interfaces. Prefer reuse of exact nano-USD arithmetic and existing validation; do not silently change historical usage reporting.
2. **A real enforcement boundary.** Define one executable bounded-call interface through which every scripted provider call passes, and the later production consumer that must use it. A test that manually updates a balance around an unconstrained provider does not prove this boundary. If the public launcher cannot expose/bound each billable request, say so: a launcher-wide opaque command cannot be declared capped from after-the-fact totals. Specify the stand-in mechanism as a separately testable prerequisite and identify the unreleased per-call integration contract; leave production enablement blocked. Do not promise a private engine implementation.
3. **Trusted admission inputs.** Specify strict run/owner/settings/config/price identity, fresh opt-in, integer money units/ranges and exact route/served-ID matching. Define how current configuration is revalidated before each reservation. Consent and caps never come from a saved preset, default, copied historical Start or provider-controlled billing label. An untrusted pin or marker is not sufficient proof.
4. **Bound before dispatch.** Derive a conservative maximum charge using bounded input, enforceable output limits, cache/extra billable categories, price freshness and any price-window boundary. Reserve that maximum atomically before sending. Unknown billing components, unenforceable limits or unknown/stale price without a reviewed bound refuse. Do not use floating point, assumed zero cost or best-effort post-response cancellation to claim a hard cap. Specify the scope of provider assumptions explicitly; an unbounded provider must remain unavailable.
5. **Whole-run accounting.** Cover calls, retries and parallel roles sharing one budget; exact-boundary positive; over-budget zero dispatch; replayed call IDs and changed-body conflicts; durable reservation/settlement, duplicate responses and ambiguous completion. Never refund an uncertain dispatched request merely because the caller crashed or timed out. On recovery, either prove retained authority/accounting or refuse further spending. Choose and justify the minimal storage/locking interface and crash protocol; a fresh in-memory counter after restart is insufficient. Separate any native persistence qualification from the cloud mechanism's tests.
6. **Bounded execution and identity.** Authenticate the requested route and compare actual served identity; mismatch or unverifiable identity fails closed, accounts conservatively for any dispatched charge and blocks subsequent calls. Specify streaming, timeout/abort, Stop, late response and exactly which requests may already be in flight. Define cancellation acknowledgement and resource ownership; no automatic retry/fallback around a refusal.
7. **Independent proof.** Script a deterministic fake provider with observed request counts, usage, served identities, delays and failures. Test multiple calls and retries exhausting a cap; concurrent barrier contention (20 callers, observed winner/loser paths); restart at reservation/dispatch/settlement; duplicate/changed IDs; stale price, price-window/DST boundary, missing consent, forged/cross-run pin, multiple paid routes, identity mismatch, missing usage, overflow and Stop. Work out expected nano-USD totals independently. Include free/subscription positive behavior so the paid gate cannot block unrelated free work.
8. **Safe integration packet.** Enumerate exact NEW module/test files, actual later consumers, interfaces, commands and helper ownership; list integration prerequisites separately. Register cloud tests in the existing appropriate lane without weakening it. Retain native paid-readiness=false. Do not award `CAPPED-PAID-RUN-GREEN` from stand-ins. If a complete buildable cloud scope cannot be specified from this base, report the exact technical gap as BLOCKED rather than inventing support.
