## IP-01 — jsonwebtoken 9.0.3 in the Access verifier

Seven adversarial tests were written against the real verifier with a live
2048-bit RSA keypair. All seven pass.

### The four attacks the brief invited

| # | Attack | Result |
|---|---|---|
| 1 | Flooring `clockTimestamp` extends a token's life | **Held.** Rejected at `exp` and across the sub-second window above it. |
| 2 | A decision is made from the unverified header | **Held.** |
| 3 | Future-`iat` refusal is unreachable | **Held, and load-bearing.** |
| 4 | A library error escapes or leaks | **Held.** |

**On (1).** The brief's reasoning is correct and was verified rather than
accepted. `jwt.verify` with `clockTimestamp: Math.floor(nowMs / 1000)` is the
*more lenient* of the two expiry checks, because flooring can only move the
comparison timestamp earlier. The retained unfloored check binds:
`expires = min(claims.exp, claims.iat + maxSessionSeconds)` is always `<= exp`,
and `expires <= now` uses the unfloored `nowMs / 1000`. For `nbf` the floored
check is the *stricter* of the two; both agree at the boundary.

**On (2).** The only use of `jwt.decode` output is `keys.get(header.kid)`
against a fixed deployment-supplied map, plus the strict zod header schema.
`jwt.verify` independently re-enforces `algorithms: ["RS256"]` over the signed
bytes. No other decision reads the unverified header.

**On (3).** jsonwebtoken does not check `iat`. This was verified positively: the
same token that the verifier rejects is *accepted* by
`jwt.verify(token, publicKey, { algorithms: ["RS256"], clockTimestamp })`.
The retained hand-rolled `claims.iat > now` check is what rejects it, and is
therefore load-bearing rather than vestigial.

**On (4).** Expired, not-yet-valid, bad-signature, unknown-`kid`, malformed and
empty tokens all surface as `WebAccessError` with both `code` and `message`
exactly `authentication_required`. No `TokenExpiredError`, `NotBeforeError` or
`JsonWebTokenError` escapes, and no library message text leaks.

### Three additional attacks, all refused correctly

- **HS256 algorithm confusion** — a token signed with an HMAC secret and
  `alg: "HS256"` is refused, by both `headerSchema`'s `z.literal("RS256")` and
  `algorithms: ["RS256"]`.
- **`jku` header injection** — a header carrying `jku` pointing at an
  attacker-controlled key URL is refused by `headerSchema.strict()` before
  verification is attempted.
- **Non-canonical base64url** — a padded signature segment and a bit-flipped
  final character are both refused.

Also confirmed: a bare-string `aud` is still refused. jsonwebtoken would accept
it; the retained `z.array(z.string()).min(1).max(16)` does not.

### The `canonical()` refactor is a small improvement

The previous code checked canonicality on `h` and `c` via `decode()`, and on `s`
by an explicit round-trip. `parts.every(canonical)` now applies the same check
uniformly to all three segments.

### The "known gap" is closed

The brief asked the reviewer to re-run the two dual-address verifier tests that
exist on `codex/idea-abs-workflows` but not on the committed branch. This was
resolved by test-merging rather than by re-running:

```
git merge-tree --write-tree codex/idea-abs-workflows stage1/ip-01-jsonwebtoken
```

Conflicts are confined to **`package.json` and `pnpm-lock.yaml`** — routine
dependency merging. `src/web/v1/access-verifier.ts` merges cleanly. The merged
file was extracted and the codex branch's `tests/web-access.test.ts` run against
it: **6/6 pass**, including both dual-address tests.

**Correction to the brief.** The divergence is not "two extra tests." The codex
branch's `access-verifier.ts` exports a function that `main`'s does not —
`captureWebOrigins` (+10 lines), which IP-01 was never written against. It
happens to sit above `VerifiedWebIdentity`, disjoint from the changed lines, so
it merges without conflict. Describe this as a code merge, not a test re-run.

### Minor note — UTF-8 strictness lost

The removed `decode()` used `new TextDecoder("utf-8", { fatal: true })`, which
rejected invalid UTF-8. jsonwebtoken's decode is lenient, so invalid sequences
now become U+FFFD rather than being refused. Only the legitimate issuer can
reach this, since the signature must still verify, so severity is low — but it
is a strictness loss not listed among the deliberately delegated items.

### Scope observation — not a request to reopen DR-05

The change delegates roughly 14 lines of `node:crypto` work and retains
everything else: key hygiene (RSA-only, private-component rejection, 2048-bit
minimum modulus, `kid` uniqueness), the Cloudflare `type: "app"` claim,
`validUntilMs` freshness, session clamping, canonical encoding, uniform error
flattening, and the token digest. In exchange it adds nine transitive packages
to the authentication path.

DR-05 weighed this and chose; this review does not reopen it. But the packet's
framing — "remove superseded standard JWT decoding/signature work" — understates
how much is retained and overstates how much is removed. The retained surface is
larger than the delegated surface.

## IP-04 — node-postgres 8.23.0

### Finding 1 — HIGH, new: the rehearsal probe can never close

**`src/web/v1/private-rehearsal-probe.ts`, `createProbePool`.**

`reserve()` returns `{ query }` only. The checked-out `PoolClient` is **never
released**, and `end` is `() => pool.end()`.

pg-pool's `end()` resolves only when `_clients.length === 0`. A checked-out
client remains in `_clients` until released. Demonstrated directly against the
installed `pg-pool@3.14.0` with a stub `Client`:

```
client checked out, never released -> pool.end() resolved? false
after release()                    -> pool.end() resolved? true
```

Consequence: `createRehearsalProbe(...).close()` loses its 5-second
`Promise.race` **every time**, `closed` is never set to `true`, and the probe
throws `RehearsalProbeError("probe_uncertain")`. The probe is unusable against a
real server, and the failure presents as a database problem rather than as a
driver-adapter bug.

**No test can observe this.** All six tests in `tests/web-rehearsal-probe.test.ts`
inject a fake `createSql` factory. `createProbePool` has zero coverage and is not
exported. The test at line 37 captures `options.onclose` and invokes it by hand,
which proves the probe *reacts* to onclose and proves nothing about whether the
node-postgres events are wired to it — which is exactly the property the brief
asked the reviewer to confirm.

Suggested fix — hold the client and release it before ending the pool:

```ts
let held: PoolClient | undefined;
return {
  async reserve() {
    const c = await pool.connect(); held = c;
    c.on("end", onclose); c.on("error", onclose);
    return { query: (config: { text: string; values: unknown[] }) => c.query(config) };
  },
  end: async () => { held?.release(true); await pool.end(); },
};
```

**On the event set itself** (the brief's explicit question): `pool.on("error")`
covers errors on idle clients, and `end`/`error` on the reserved client cover
server-initiated disconnect — FIN arrives as `end`, RST or a protocol error as
`error`. The event choice is sound. The defect is the leak, not the wiring.

`createProbePool` should be exported so this path can be tested at all.

### Finding 2 — HIGH, confirmed: the `preCommitCheck` merge hazard is a blocker

The brief flags this honestly and calls it "one line, silent if missed." All
three components confirmed:

1. **The contracts differ as described.** `codex/idea-abs-workflows` declares
   `preCommitCheck: () => void | Promise<void>`, with the comment *"Wrappers must
   return/await the check too; rejection must prevent commit."* `main` declares
   `() => void`, and the new `inTransaction` calls it synchronously.

2. **TypeScript will not catch it.** A function returning `Promise<void>` is
   assignable to a parameter typed `() => void`. A minimal case compiles clean
   under `--strict`. `@typescript-eslint/no-floating-promises` will not fire
   either, because at the call site the declared return type is `void`.

3. **There is a live async caller.** `src/web/v1/task-coordinator-lifecycle.ts:139`
   passes `async () => { check(); await precommit(); check(); }` into the real
   client's `transactionWithPreCommitCheck`. Under a synchronous
   `inTransaction`, that promise is dropped, `COMMIT` proceeds immediately, and
   the lifecycle interruption that exists to prevent the commit does not fire —
   defeating the `task_coordinator_save_uncertain` guard silently.

Recommend raising this from "hazard to carry forward" to a **merge blocker with
a named owner**, resolved in the merge commit itself: `await preCommitCheck()`,
with the local contract widened to `() => void | Promise<void>`.

### Finding 3 — MEDIUM, new: a failed `BEGIN` returns the connection to the pool

**`src/persistence/database.ts`, `inTransaction`.**

`await connection.query("BEGIN")` sits outside the error handling. If it throws,
control passes straight to `finally` with `discard === undefined`, so
`connection.release(undefined)` returns the connection to the pool.
Demonstrated:

```
not ok 1 - a failed BEGIN discards the connection rather than returning it to the pool
ok 2 - a failed COMMIT discards the connection
ok 3 - a clean transaction returns the connection to the pool
```

This contradicts the module's own comment — *"A connection whose transaction did
not end cleanly is discarded rather than reused"* — and is inconsistent with
`private-pg-driver.ts`, which poisons on any query failure. `BEGIN` fails when
the connection is unhealthy or the session is already in an aborted transaction,
which is precisely when it must not be reused.

```ts
try { await connection.query("BEGIN"); }
catch (beginFailure) { discard = beginFailure as Error; throw beginFailure; }
```

### Finding 4 — MEDIUM, new: `close()` lost its shutdown deadline

`close: () => sql.end({ timeout: 5 })` became `close: () => pool.end()`. The
five-second bound is gone, and by Finding 1's mechanism `pool.end()` waits
indefinitely for checked-out clients. A hung query now hangs shutdown.

The brief correctly notes this path is not behind `bounded-database` and has no
whole-transaction deadline. It does not note that the path previously had a
*close* deadline and no longer does. That is a lost bound, not a pre-existing
absence.

### Finding 5 — LOW, correction: the primary-check rationale is wrong

The brief states the check now runs "once per physical connection … rather than
once at startup, so a node demoted later is caught."

`target_session_attrs=primary` also checks once per connection, not once at
startup. The new code is **equivalent**, not stronger. Further, the `WeakSet`
means a validated connection is never re-checked, so "a node demoted later is
caught" holds only because demotion terminates existing connections — an
assumption neither the brief nor the code comment states.

The implementation is fine. The justification should be corrected in both places
so nobody later relies on a property that is not there.

### Finding 6 — LOW: two bigint type annotations are now inaccurate

`pg` returns `int8` as a **string** (confirmed against the installed
`pg-types`: `int8 -> String "42"`, while `int4 -> Number 42`).

`src/web/v1/task-assignment-coordinator.ts:297` types `epoch: number` and
`:302` types `lease_epoch: number`. Both are strings at runtime under pg.

Every current comparison coerces defensively — `lease.epoch !== Number(row.epoch)`,
`attempt.leaseEpoch !== Number(attemptRow.lease_epoch)`, and likewise for
`version` and `attempt_number` — so there is **no live bug**. But the
annotations are false, and they invite an un-coerced comparison later, where
`"10" > "9"` is `false`. `src/audit/audit-store.ts`,
`src/harness/v1/store.ts` and `src/node-control/job-event-service.ts` already
use `number | string`; these two should match.

## Checked and *not* findings

Recorded so the next reviewer does not re-spend the time.

- **`count(*)` int8 drift.** Already defended: the Postgres paths use
  `count(*)::text` and type the result `string`.
- **pg's local-timezone `DATE` parsing.** `pg` parses OID 1082 to a local-midnight
  `Date`, which can shift the calendar date. No bare `DATE` columns exist in
  `db/migrations`, so this does not bite.
- **Double `terminate()`.** Does surface a raw
  `"Called end on pool more than once"` from pg-pool, but
  `bounded-database.ts` guards with `if (closing) return closing` and the
  contract states "Called once." Not a defect.
- **`release(discard)` passing an `Error`.** Correct node-postgres usage; any
  truthy value destroys the connection.
- **terminate/acquire races in `private-pg-driver.ts`.** The window where
  `terminate()` runs during `await assertPrimary` was probed. The `if (closed)`
  re-check after the primary check closes it, and the `done` flag makes the
  discard exactly-once. The ordering comment at lines 72–73 is accurate.
