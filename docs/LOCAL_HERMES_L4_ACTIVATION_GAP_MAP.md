# Local Hermes L4 activation gap map

**Status:** the canonical Control Room lifecycle is assembled in source. The
installed Hermes process-custody route is not yet implemented, so this is not a
live worker and no owner action is useful yet.

## What is already one connected source path

The existing packages already form one installation-owned path:

1. `local-hermes-installation-binding.ts` binds the exact installation,
   topology, release, selected worker, runner configuration, sanitized
   qualification evidence, recovery proof and healthy service observation.
2. `private-installed-local-hermes-runtime-composer.ts` reconstructs the
   ordinary planner, one PostgreSQL/pg-boss queue, local delivery, terminal
   staging, durable publication, result inspection, owner review and correction
   services from protected installed data.
3. `hermes-021-private-installation-composition.ts` accepts that reviewed graph
   only through its one-use private capability and supplies the same canonical
   local queue lifecycle used by the application.
4. `private-installed-local-operator-loader.ts` joins protected installed
   configuration to the retained native installation journal before the
   operator can start.
5. `private-local-hermes-startup-reverification.ts` rereads the settled setup
   and final-review evidence and rejects a changed delivery, runner, worker,
   queue role/concurrency, topology or release before startup effects.

Result publication, pending review, correction and restart reconciliation are
therefore not missing assembly seams. Adding another wrapper, queue, scheduler,
database or readiness record would duplicate accepted code without making the
worker safer or more operational.

## The one remaining source blocker

The current path-based Hermes launch cannot prove that the script, Python
interpreter and loaded modules are unchanged between review and execution. The
earlier owner-attended qualification remains useful compatibility evidence,
but it cannot authorize a future installed launch route with different process
custody.

The next build package is the concrete implementation described by
`HERMES_MACOS_RELEASE_SIDECAR_CUSTODY.md`:

- a deterministic, licensed, read-only image containing the complete,
  unmodified Hermes 0.21.3 runtime closure but no credentials, profiles,
  memories, skills or private configuration;
- a release-bound native host that can launch only the fixed entry inside that
  verified image, owns process-group cleanup, and accepts no executable or
  runtime path from ordinary configuration;
- macOS release packaging, installed-manifest custody and a one-use capability
  that replaces the current pathname-based subprocess input; and
- adversarial tests and independent security review covering changed bytes,
  altered interpreter/modules, extra or missing runtime entries, writable
  images, wrong release/architecture, helper loss, descendant cleanup and
  capability replay/forgery.

Until that package is accepted, the installed route must refuse before starting
Hermes. No saved path, provider/model value, claimed readiness record or prior
qualification result may clear this blocker.

## Exact later owner gates

These are future owner-attended steps, not actions requested by this source
package:

1. Authorize a bounded public-runtime inventory and packaging run. It must not
   inspect or copy credentials, profiles, memories, skills or private data.
2. Install the reviewed, architecture-specific Hermes sidecar/runtime image in
   the protected Control Room installation and materialize the manifest that
   binds its exact release bytes.
3. Complete the existing seven setup stages against the real installation:
   database authority, protected data, first owner, recovery, platform service,
   Hermes readiness and final review.
4. Attend one fresh text-only Hermes qualification through the installed
   sidecar using the privately selected profile/model/provider/work folder.
   The previous pathname-based qualification cannot replace this step.
5. Separately enable the worker and authorize one harmless bounded real task.
   Its saved result must enter ordinary pending review, and any correction must
   reuse the same task/run authority rather than starting a hidden retry.

Downloads, installation, native staging, credentials, persistent services,
database operations and the first real task remain outside source-only work and
require their separately scoped owner authorization.

## Reuse decision

Retain the existing Control Room Hermes adapter and lifecycle. Prior source
inspection found Hermes WebUI and Hermes Desktop useful as conservative
session/status presentation references, but neither provides Control Room's
installation authority, canonical queue, durable receipt, review or native
macOS process custody. No donor runtime should replace the assembled path.
