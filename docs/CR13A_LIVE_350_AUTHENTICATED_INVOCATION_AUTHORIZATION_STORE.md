## Purpose

LIVE-340 requires an authenticated one-use authorization and independent replay state before any source lookup. LIVE-350
implements only the durable registration half of that boundary. It accepts an already sealed authorization, verifies
its exact authenticated body, and atomically records the authorization plus a digest-only nonce reservation in the sole
global database model. It does not decide who may issue an authorization and cannot consume one.

## Fixed authorization body

One exact versioned body binds the accepted LIVE-330 source product, accepted LIVE-340 contract product and review,
tenant, project, connection, node, target platform family, target runtime family, candidate, attempt, the exact
`observe_target_runtime_once` operation, authorization ID, nonce digest, issued time, not-before time, expiry time, and
sealing-key ID digest. The body contains no raw nonce, key, signature material, native value, locator, endpoint,
credential, command, or provider content.

The authorization is authenticated by an HMAC tag under one separately protected 32-byte authorization key supplied to
the store. A distinct protected 32-byte state key authenticates persisted records, reservations, and the stream head.
Both keys are captured defensively and are never persisted, returned, logged, digested into public evidence, or
generated by this module. LIVE-350 supplies no production issuer. Tests may create exact synthetic envelopes with
repository-only keys.

## Durable registration and replay reservation

The repository implementation uses the existing `DatabaseClient` PostgreSQL abstraction and one new migration. A
single transaction locks the tenant, rejects any conflicting authorization ID or nonce digest, inserts the immutable
authorization row, and inserts one separate immutable nonce-reservation row. Exact replay of the identical sealed body
is inert and returns the original sanitized registration receipt; changed reuse of either identity is a conflict.

Rows are bound by body digest and record HMAC. The nonce table stores only the digest and authorization reference. SQL
uniqueness enforces one tenant-scoped use of each authorization ID and nonce digest under real PostgreSQL concurrency.
Tables are append-only. LIVE-350 has no update/delete/cleanup method and cannot mark an authorization consumed.

PGlite proves deterministic schema, transaction, exact replay, conflict, partial deletion/reordering, hostile-input,
restart, and local concurrency behavior only. It is not production evidence. Whole-database rollback handling belongs
to the accepted PostgreSQL backup/recovery architecture and real PostgreSQL rehearsal remains separately gated.

## Public boundary

The store may return only an immutable sanitized registration receipt containing opaque references, digests, canonical
time bounds, and negative authority flags. A receipt is evidence of durable registration, not an invocation permit.
There is no public lookup-by-nonce, listing, unseal, consume, delete, retry, source, callback, callable, or native bridge.

A disabled status records zero configured production keys/databases, zero source lookup/invocation/native reads, zero
physical attempts, zero listeners, and false approval/qualification/candidate/activation/network/command/lease/
execution grants.

## Non-collapsible order

LIVE-350 ends after authenticated registration and replay reservation. Later blocks must separately implement and
review final trusted-time/lineage validation, atomic consumption, post-transaction time recheck, same-module lookup,
one source invocation, private observation handoff, attestation/signature, durable attestation replay, candidate
assembly, owner authorization, physical qualification, and runtime activation.

## Prohibited in LIVE-350

LIVE-350 must not import or modify LIVE-330; import `node:process`, `node:os`, or another native/effect module; create or
read a real production key; issue an authorization; trust caller time as current time; consume or revoke an
authorization; add a source map lookup or invocation; inspect a descriptor; read or expose native material; create an
observation or attestation; assemble a candidate; implement owner authorization; open a listener; wire application,
API, worker, scheduler, Idea Lab, Hermes, startup, or runtime use; contact a provider; connect to production PostgreSQL;
deploy; clear a blocker beyond the registration-store and replay-reservation implementation facts; or claim PGlite as
production proof.

## Acceptance

Completion requires exact LIVE-340 product/review binding; exact immutable authenticated input and sanitized receipt;
defensive key and hostile-input handling; atomic authorization/nonce insertion; inert exact replay; changed-replay,
tamper, partial-deletion, duplicate, and foreign-scope rejection; append-only migration guards; PostgreSQL-compatible queries;
local PGlite restart/concurrency evidence; no downstream consumer or native import; explicit negative production and
authority truth; full producer verification; and a different independent report-only zero-repair review.

Acceptance permits ordinary integration of the repository store and migration only. It grants no issuer, consumption,
trusted-time decision, source lookup/invocation, native read, observation, attestation, candidate, owner authorization,
listener, physical qualification, runtime activation, provider, deployment, or production authority.
