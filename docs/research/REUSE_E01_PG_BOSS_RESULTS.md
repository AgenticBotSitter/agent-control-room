## Disposition

**Advance pg-boss 12.30.0 to real-PostgreSQL comparison; do not adopt it yet.** The downloaded package ran successfully against the application's existing PGlite 0.3.14. A test-only adapter inserted its job into the exact transaction used by Control Room's canonical approval/intent/audit services. ## Failed first experiment and adapter correction

The first run passed its standalone smoke test, then stalled at transaction submission. It was interrupted; it is not a pass. Installed source inspection showed that `createQueue()` evicts internal queue metadata and public `getQueue()` reads but does not populate that cache. `send()` then tries an outer-database metadata read even when an explicit transaction adapter is supplied. With a single PGlite connection held by the caller, this stalls.

The revised disposable fixture primes the cache by fetching its known-empty queue before entering any caller transaction. A guard now rejects any outer database operation while that transaction is active. This passed the seven-case intermediate run and final eleven-case run. **Empty-fetch priming is a test setup technique, not an approved production startup recipe**: fetching a live queue could claim real work. Production design must establish queue metadata before admissions and test queue creation/cache invalidation/races without depending on this assumption. Upstream was not patched.

## Required integration consequences

- Use pg-boss's `db.executeSql` transaction override for the actual INSERT. Do not open a separate pool inside the canonical commit path. Multi-statement schema initialization needs an appropriate migration connection/exec path; it does not belong in ordinary worker transactions.
- Preserve current approval/pre-commit checks and immutable audit. The experimental wrapper's unconditional synthetic submission is not a production replay policy.
- Keep canonical operation identity/dedup history longer than operational queue retention. A lost external-start receipt must reconcile with the original native identity, never automatically become a new provider call.
- Queue retry/cancel states mean delivery bookkeeping; they do not prove native termination, current authorization or safe retry of a consequential effect.
- Queue schema owner/migrator, ordinary submission worker and private web roles must be designed and tested separately. These tests used fixture owner access, not deployed restricted roles.

## Not run / next gate

Real PostgreSQL multi-connection locking, process crash/restart, worker eligibility/capacity, simultaneous consumers, dead-letter operations, actual scheduler tick/DST/downtime policy, long review/revision, version upgrade/drain, backup/restore and uncertain native-start reconciliation are **not established by E01**. A client restart against one surviving in-memory database is not a crash-recovery or restore test.

Next required authority: a bounded disposable local PostgreSQL cluster, no production credentials, no standing/autostart service, no VPS changes, with exact data directory/lifetime and verified shutdown/cleanup. Package download permission has been granted; server initialization/startup has not. Prepare the smallest suitable local PostgreSQL method before asking to activate it. Do not install a global service or Docker implicitly.
