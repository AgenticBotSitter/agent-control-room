## What the new evidence supports

- The selected `pg-release-destroy` run uses actual Pool.connect/end and lease.release(true), actual CR boundedDatabase and one observed active server query plus one waiting checkout. Receipt reports close resolved183ms, one SQL issue/lease/release/terminate call, zero tracked pending/pool waiters/clients, rejected application operations and refused future work. Zero counters are recorded observations, not individually asserted invariants in the fixture; parent exit0 alone is not their proof. The receipt contains the decisive values.
- The wrapper prevents application work after invalidation. Removing a lease from the research Set before release(true) makes the later wrapper release a no-op for that lease. pg-pool's `_releaseOnce` prevents genuine double release; `_release` removes a client when passed a truthy destroy argument, while `_remove` owns client shutdown. This is maintained pool behavior, not private socket manipulation.
- Pending checkout tracking is meaningful: pg-pool's configured connectionTimeoutMillis removes a pending queue callback and rejects it (index.js:198–231). The fixture intentionally uses200ms, leaving margin below the500ms CR close bound, and waits all tracked pending promises before reporting termination. The observed183ms is consistent with a checkout already waiting roughly20ms when close starts, but no internal timing trace proves that exclusive cause.
- The uncast source fixture uses actual maintained drivers and bounded wrapper with synthetic timestamptz/UUID rows and the same operator/unknown-parameter contexts identified in real outbox/recovery SQL. It is not actual DeliveryStore/recovery execution. The normalized receipt preserves both blanket text-typing failures, plain/pg passes, and observation-only meaning of exit0. Unlike the release receipt it is a normalized summary pointing to tool chunk1de759, not raw stdout retained in this file; that reduces independently inspectable diagnostic detail but is explicitly labeled, not misrepresented as raw capture.
- A server session remains after close; the draft correctly does not infer current active execution, instantaneous cancellation, rollback or failed-write nonexecution. Explicit cleanup later observes absence, and the retained receipt confirms owned cluster stop/removal.

## Boundaries of the demonstrated shutdown composition

This is one acquired lease and one already waiting checkout. It does not cover a connection still being established, a checkout resolving during the release snapshot, acquisition rejection during close, multiple pools/leases, repeated close or transaction COMMIT uncertainty. Promise.allSettled observes its snapshot; it is not by itself a universal proof that no later acquisition can produce a lease. The actual wrapper's late-lease release and pool-ending behavior are relevant existing mechanisms, but the concrete implementation needs the draft's race tests and exactly-once release assertions. Do not copy the fixture's200/500ms values into production or claim ordinary Pool.end alone now meets the contract.

## Strongest alternatives and fair cost

Targeted Postgres.js public typing remains viable: preserve inferred timestamp/UUID parameters and type only explicitly identified serialized JSON parameters. Current DatabaseSession lacks semantic type metadata; changing that or selected callers is real integration work, but its cost has not been measured. This alternative must not be dismissed as impossible or as needing a whole SQL parser. The existing queue-specific bridge and callers already knowing JSON fields are plausible limited annotation seams.

A supported custom JSON type serializer is also a concrete alternative, not an upstream fork. It might pass through pre-serialized strings while using maintained JSON serialization for ordinary object inputs; exact handling of scalar strings, arrays, nulls and public type-OID registration still needs a deliberately specified policy and parity tests. It is source-screened only, not proven slower, larger or broken. The draft fairly leaves it viable and explains the provisional preference: pg directly fits the current unannotated caller semantics, while a supported public-release lifecycle composition has now worked on a representative adverse seam. No fabricated resource score or universal cost victory is needed for this reversible direction.

## Conditional implementation/removal acceptance

Keep the actual bounded wrapper, same transaction client, precommit checks, unknown-outcome quarantine, explicit target/session configuration and no-fallback/no-replay rules. The direct runtime dependency/notices and all Postgres.js runtime, test and packaging consumers need explicit inventory before removal; current removed production lines remain zero. The draft correctly distinguishes binary/dependency rollback from replaying uncertain writes. Its1–3day estimate is planning judgment, not measured comparison evidence.

Actual caller regressions, late/failed checkout and active/queued shutdown races, uncertain COMMIT/reconciliation, preserved session settings and PG17/current-role deployment remain implementation gates. Those limits do not prevent the narrow conditional driver direction; they prevent calling it shipping-ready. Root retains final selection and integration authority.
