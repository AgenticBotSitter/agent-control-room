# Release signing

Control Room uses one installation-scoped Ed25519 key for both weekly release artifacts and connector self-updates. The private key is generated during the root-owned installation step and remains in `updater-state/release-signing-key.pem` with mode `0600`. The public trust record is embedded in the digest-verified connector bundle. Enrollment must return that exact record; the gateway can never select a different key. The connector then stores one trust record beside the machine-wide launcher, shared by every profile on that machine.

The first installation still relies on the design's pinned commit and checksum rule: its installation key does not exist until that install runs. Every later signed release is checked against the pinned installation public key and the installation's non-decreasing version floor.

This signature is the artifact-trust step, not a substitute for updater source trust. The R18 source path must still use its dedicated read-only repository credential and compare the archived tree with the pinned commit before a build is eligible to be signed. The connector advertisement also signs the exact 40-character source commit as `builtFrom`.

## Installation bootstrap

Run as root after creating the updater design's installation layout: `updater-state/` is root-only `0700`, while `Protected/` and `Protected/config/` are root-owned `0750` and group-readable by `_controlroom`. `gateway.json` may be `0640`; the generator validates it but never rewrites it.

```sh
pnpm install:release-key -- \
  --protected-root /absolute/install/Protected \
  --gateway-config /absolute/install/Protected/config/gateway.json \
  --version-floor 1.0.0
```

The operation is retryable. A stop after the private key is created retains that key; a retry derives and publishes its public half. Concurrent callers converge on the first key rather than replacing it.

If `release-trust.json` already exists, a retry succeeds only when the key, epoch, floor and revocation list are byte-identical. A retry after rotation or a floor change refuses with `trust_exists`; rotation is the only path for changing trust.

### Custody table

| Item | File | Mode / reader | Purpose |
|---|---|---|---|
| Installation release private key | `updater-state/release-signing-key.pem` | root `0600` | Signs release checksum sets, connector advertisements, rotations and revocations. Never readable by the gateway or workers. |
| Signing selector | `updater-state/release-signing.json` | root `0600` | Selects the absolute private-key path for the root updater. |
| Public release trust | `Protected/config/release-trust.json` | root:`_controlroom` `0640` | Read by the gateway and embedded into connector bundles. Only root writes it. |
| Gateway configuration | `Protected/config/gateway.json` | root:`_controlroom` `0640` | Contains gateway configuration but no private signing material and is not rewritten by key generation. |

## Weekly release signing

The release directory must already contain the connector bundle, updater bundle, and web build manifest. The connector's build manifest must describe the exact connector bytes. The signing configuration is a `0600` JSON file generated by installation; it selects the private key by absolute path.

```sh
pnpm release:sign -- \
  --release-directory /absolute/release \
  --version 1.2.3 \
  --config /absolute/install/updater-state/release-signing.json \
  --connector /absolute/release/connector-1.2.3.mjs \
  --connector-manifest /absolute/release/connector-manifest.json \
  --connector-min-version 1.0.0 \
  --updater /absolute/release/updater-1.2.3.tgz \
  --web-manifest /absolute/release/web-build-manifest.json
```

This writes:

- `SHA256SUMS`, with exactly the three release artifacts;
- `SHA256SUMS.sig`, an Ed25519 signature bound to the release version and exact checksum-file digest;
- `connector-release.json`, the connector updater's signed version/file/size/digest/source/minimum-version advertisement;
- `RELEASE_NOTES.signing.md`, including the connector SHA-256 and release key ID.

Before unpacking or using a later release, the installer verifies the signed set with the pinned private trust file:

```sh
pnpm release:verify -- \
  --release-directory /absolute/release \
  --trust /absolute/install/Protected/config/release-trust.json \
  --installed-version 1.1.0 \
  --built-from 0123456789abcdef0123456789abcdef01234567
```

The verifier requires the exact checked-out commit and a root-owned `0700` staging directory. Its `SHA256SUMS.sig` binds both that commit and the checksum-file digest. A normal update must be newer than the installed version and at or above the durable trust floor. An owner-approved rollback is a separate call using `--allow-rollback`; never infer rollback authority from a release signature.

Only after the verified release has installed successfully, raise the durable floor atomically:

```sh
pnpm release:record-installed -- \
  --trust /absolute/install/Protected/config/release-trust.json \
  --installed-version 1.2.3
```

Concurrent completions serialize, and a lower or equal completion can never reduce the floor.

Build the connector before signing and embed the public trust record:

```sh
pnpm build:fleet-connector -- --release-trust /absolute/install/Protected/config/release-trust.json
```

The connector bundle imports the same connector-advertisement verifier for its self-update module. Both paths therefore use the same key encoding, exact version comparison, signature material, version floor, key epoch, and revocation semantics. The gateway reads `connector-release.json`; there is no second connector key generator or `signature.json` format.

Signing and verification reject symbolic links, non-regular or multiply linked files, unstable files, oversized files, malformed manifests, a non-Ed25519 key, and a key or key-selection configuration that is not exactly `0600`.

## Rotation and revocation

`createReleaseKeyRotationV1` produces a domain-separated record for the new public key, next epoch, and non-decreasing version floor, signed by the current private key. `applyReleaseKeyRotationV1` verifies that old-key signature before accepting the replacement and adds the retired key to the revocation list.

These records support release-trust administration, but connector machines do
not apply key rotation in v1. A machine refuses a rotation record before changing
its pinned trust, so its already-installed connector remains runnable. To change
the release key, reinstall the connector on every machine through the trusted
owner installation path. An ordinary installed-release record changes only the
version floor; it never changes the pinned key identity, and both gateway and
machine floors are merged upward.

`createReleaseKeyRevocationsV1` produces an epoch-ordered revocation list signed by the active key. `applyReleaseKeyRevocationsV1` verifies it, unions it with prior revocations, and refuses revocation of the active signer. Release and connector verification reject any selected key ID present in the applied list.

The wire contract used by connector self-update is exported from `scripts/release-signing.mjs` as `connectorReleaseSignatureMaterialV1`, `signConnectorReleaseAdvertisementV1`, and `verifyConnectorReleaseAdvertisementV1`. Its schema and line ordering match the connector updater package so the gateway, connector, and installer do not maintain separate signing formats.

Rotation records are for planned trust administration, not recovery from a
stolen active private key: an attacker holding that key can sign a rotation too.
For connector machines, planned replacement and suspected compromise both
require reinstalling and freshly pinning through the owner's trusted installation
path. Do not present rotation or revocation as compromise recovery.
