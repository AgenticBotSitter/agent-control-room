# CR11B-AUTO-080 Disposable Hosted Qualification Preparation Contract

Status: second remediation rejected; third remediation requires a fourth different independent review

Date: 2026-08-30

## Purpose

AUTO-080 converts the independently accepted AUTO-070 fake qualification into one exact request for a later
owner-authorized, disposable hosted PostgreSQL qualification. The request is planning evidence, not authority. It cannot
select a provider, resolve a protected reference, contact a database or network, start a process, authorize cleanup, or
run the qualification.

The repository phase deliberately stops before the controlled effect. A later packet may exist only after the owner names
the exact disposable provider and resources, signs the exact bounded operations and ceilings, authorizes protected access
and cleanup, and supplies those resources outside Git and repository artifacts.

## Accepted source

Every request embeds and re-verifies:

- the complete authenticated AUTO-070 custody plan and successful no-fault fake report;
- exact accepted AUTO-070 implementation commit `20eeb148ce7ecf59a777f060eacd9245d9948cc8`; and
- exact independent-review SHA-256
  `07033f542a7e3b7167a95d3fa301b90ff3806ec49232cddc878e8fa84353f681`.

A failed or fault-injected fake cannot become a disposable qualification request. Source plan, report, scope, digest,
HMAC, chronology, or accepted-identity drift fails closed.

## Exact requested envelope

The request asks the owner to consider only:

- an owner-selected private hosted PostgreSQL provider;
- two new disposable non-production databases: the bounded qualification database and a separate isolated restore target;
- three isolated worker processes corresponding to the accepted proof-writer, proof-reader, and external-checkpoint roles;
- `SERIALIZABLE` database transactions;
- at most 40 provider calls;
- at most 1,800 seconds of live activity;
- at most 1,048,576 bytes of sanitized retained evidence;
- no production data and no public endpoint; and
- mandatory separately authorized cleanup with a cleanup receipt.

The seven operations are fixed and ordered:

1. provision the disposable database;
2. start three isolated workers;
3. run the eight accepted bounded scenarios;
4. create an isolated backup;
5. restore it to the second isolated database;
6. collect sanitized evidence; and
7. destroy the disposable resources.

No wildcard, optional provider action, arbitrary SQL, arbitrary process command, production resource, or unbounded retry
is requested.

## Ten blocking requirements

The effect-free request remains blocked until a later exact packet provides:

1. an exact owner signature;
2. an owner-selected private provider;
3. disposable resource identity;
4. a protected access reference supplied outside repository artifacts;
5. three independent service identities;

The request cannot satisfy any requirement itself. Its HMAC establishes repository integrity only and is not an owner
signature, provider credential, approval, policy, lease, or effect grant.

## Evidence and privacy

Retained evidence is limited to schema versions, safe finding/status codes, canonical digests, bounded counts, and
sanitized timestamps. Raw database output, connection strings, hostnames, provider resource identifiers, account data,
private infrastructure details, credentials, protected references, private keys, raw process output, and raw backup
material are forbidden in repository artifacts, logs, issues, pull requests, or the public projection.

The safe projection exposes the request identity, accepted fake-report identity, requested resource classes, seven
operations, ten blockers, time/call ceilings, and cleanup requirement. Every provider, network, process, database,
cleanup, live qualification, production activation, and execution capability is false.

## Chronology and replay

The request begins no earlier than the accepted fake report completion, expires strictly after issuance, remains within
the accepted AUTO-070 plan window, and lasts at most one hour. Its digest binds the complete accepted source and fixed
request. The HMAC binds request identity, scope, source digests, and time window. Exact replay is deterministic; changed
replay fails closed.

The live activity ceiling is shorter than the request window. Crossing either future authorization or live-run expiry
must stop new actions. Cleanup after expiry requires the separately typed cleanup authority described above; expiry alone
does not create cleanup authority.

## Stop boundary

This candidate imports no PostgreSQL, provider, process, filesystem, network, DNS, TLS, protected-reference, credential,
deployment, scheduler, consumer, dispatch, or execution client. It performs no install, provider selection, resource
creation, credential read, native prompt, process start, database connection, backup, restore, evidence collection,
cleanup, deployment, or external contact.

Independent review can accept only the exact effect-free preparation commit. A live attempt requires a new exact owner
authorization after review, separately supplied disposable resources, a bounded effect ledger, sanitized evidence, and
verified cleanup. No repository fixture, request HMAC, test result, chat instruction, or prior general authorization can
be relabelled as that authority.

## Acceptance boundary

An independent reviewer must verify the exact source chain, fixed operations and blockers, request ceilings, fail-closed
chronology and substitution behavior, accessor/Proxy rejection without caller behavior, sanitized projection, and the
absence of any live-effect path. Any finding keeps AUTO-080 open and no live attempt may begin.
