1. WHY THIS IS A RE-SCOPE AND NOT A THIRD FIX ROUND
--------------------------------------------------------------------------------
Two fix rounds of the static search_path audit each closed the reported holes,
and each following review found new ones:

  reports/reviews/420-98bc7dd-8859ad7.md
    - ALTER FUNCTION ... SECURITY DEFINER in a LATER FILE, on a function the
      CREATE had left unpinned
    - a later ALTER FUNCTION ... SET/RESET search_path overriding the CREATE's
      own pin
    - nested comments
    - quoted identifiers

  reports/reviews/420-98bc7dd.second.md
    - kit defects, listed in section 4 below

A regex model of PostgreSQL SQL cannot be made sound. Each fix round closed the
reported shape and left the parser still unable to answer the question. The
question PostgreSQL can answer exactly is "what is this routine's effective
configuration", so the gate now asks PostgreSQL.

2. THE GATE IS NOW A CATALOG AUDIT
--------------------------------------------------------------------------------
scripts/check-migration-search-path.mjs applies every migration in
db/migrations/ in ledger order, plus the role files, to a disposable
PostgreSQL 17 cluster, and then runs securityDefinerAuditLive over pg_proc:

  every routine with prosecdef, or prorettype in (trigger, event_trigger),
  in the app schemas, must have a proconfig search_path element whose LAST
  element is the bare identifier pg_temp.

This is PostgreSQL's effective configuration after every ALTER and RESET,
across files, with real identifier parsing. The four reported findings are
therefore not closed — they cannot arise. The catalog is the parser.

With no connection arguments the gate OWNS its cluster: it builds, audits, and
tears it down through the kit's own runner, and it REFUSES (exit 1) when
PostgreSQL 17 is not usable rather than passing on a machine that never looked.
A caller may still pass --host/--port/--user/--database to audit a cluster it
already owns, which is how the kit's own tests reuse one cluster. Either way a
zero-row catalog is refused, so an un-migrated database cannot pass vacuously.

CI placement: the gate moved OUT of the `route` job, which had no PostgreSQL,
and INTO the attack-test-kit lane, which already installs PostgreSQL 17 (line
286 of .github/workflows/ci.yml). No second 10-minute job was added.

4. proconfig IS PARSED EXACTLY
--------------------------------------------------------------------------------
proconfig is a text[] of name=value elements. The search_path value is split as
a GUC list: a comma list, double quotes respected, case-sensitive once quoted.
The last element must be the BARE identifier pg_temp.

Falsified decoys, both now caught by the gate against a real cluster:
  SET search_path = 'public, pg_temp'   one schema literally named
                                         "public, pg_temp", with pg_temp
                                         searched FIRST — the exposure
  SET search_path = public, "PG_TEMP"    a different schema from pg_temp;
                                         closes nothing
Also caught: pg_temp present but not last.

Recorded from a live database: PostgreSQL drops redundant quoting from an
identifier, so SET search_path = pg_catalog, "pg_temp" stores the bare
search_path=pg_catalog, pg_temp. The catalog therefore never produces the
quoted form, and requiring the bare one cannot reject a real routine — it only
prevents a value that merely LOOKS like the pin from satisfying the check.

A RESET removes the element entirely. proconfig is then null or holds only
other settings, and a null there is a real answer about an unpinned routine,
not a missing measurement. Verified: no message is emitted for a null; the
routine is reported without_a_search_path_clause.

THE ASSERTION IS PER ROUTINE, NOT THE EXIT CODE. With an empty allowlist the
gate also fails on the 23 shipped violations, so a non-zero exit alone proves
nothing: a scenario whose own routine stopped being flagged would still fail
for the other 23. Each scenario therefore names the identities the gate must
REPORT, and the test fails when the name is missing. This is what makes the
three mutations in section 8 bite at the gate level.

Controls, because a gate that failed on everything would pass all nine:
  - a correctly pinned routine adds no violation and is not named (control
    asserts unpinned stays at the 23 the migrations already ship)
  - the real migrations with the real allowlist pass with exit 0
  - a database whose migrations were never applied is refused
    (search_path_gate_empty_catalog)

Kit scenarios, each real:
  - pg_ctl start exits 1 after launching -> no postmaster survives
  - two kit clusters on one port -> the second refuses
  - mutation timeout with a live kit cluster -> the cluster is stopped
  - a failing unmutated command -> invalid test command
  - concurrentWriters with an always-throwing writer -> fails
  - an allowlisted routine passes until its expiry

9. SELF-REVIEW
--------------------------------------------------------------------------------
What I verified myself, and how.

The catalog is the right source, and I checked the premise rather than trusting
it. Before writing the gate I probed a live cluster for how PostgreSQL actually
records a search_path: proconfig is a normalized text[], public, pg_temp is
stored as ONE quoted array element, and an unresolvable identifier is stored
with its quotes and original case. The parser was written to that, not to a
guess. The whole point of the change is that it does not depend on a model of
the SQL, so I was wary of writing a second model into the value parser; the GUC
list split is 30 lines and is exercised by the two decoys against a real
cluster.

The per-routine attribution is the change I am most glad I made. My first
version of the attack-scenario test asserted only that the gate exited non-zero.
I then disabled the prosecdef branch, and the scenario test PASSED — because the
cluster already carried the 23 shipped violations, so the gate failed for
unrelated reasons and the mutation hid. The exit code was not evidence of
anything. Every scenario now names the identity the gate must report. That is
the difference between a test suite that would have shipped a half-dead gate and
one that does not, and it is worth stating plainly: M1 passing the original
scenarios means the original scenarios were near-vacuous.

Three identity expectations I wrote from memory were wrong and PostgreSQL was
right. I had expected pg_get_function_identity_arguments to return
probe.later_reset(uuid) and probe.cross_file(integer). It returns
probe.later_reset(p_id uuid) and probe.cross_file(a integer) — it keeps the
DECLARED parameter name and the display form of the type. I asked the live
database rather than adjusting the code to match my guess, and the expectations
now record what PostgreSQL actually does.

Test-only bugs I introduced and fixed, in case any survive into review: a
nested /* */ inside a JSDoc block that terminated it early; a backtick inside a
template literal that terminated the string; a mutation whose text the fixture
test could see, so the "guard did not bite" case was not actually a non-bite;
a timeout marker scheduled inside the BASELINE run as well, so the baseline
failed; node -e running the leak script as CommonJS where a top-level await is a
syntax error; the leak script living inside the fixture repo, where node
--import tsx cannot resolve tsx and the command died with ERR_MODULE_NOT_FOUND
before reaching the kit (fixed by resolving the loader to an absolute path);
and a bare pending promise in the leak script, which drained the event loop and
made node exit 13 in four seconds instead of hanging.

The macOS tmpdir() finding is the one I would most want a second pair of eyes
on. My first version of the cluster reap set only TMPDIR on the child, and the
reap scanned that directory — but tmpdir() on macOS resolves through confstr to
/var/folders/... and IGNORES TMPDIR, so every run directory landed outside the
scan and the reap was a no-op that looked like a fix. The test caught it only
because it asserted the postmaster pid was actually dead afterwards. The runner
now honours ATTACK_KIT_RUN_ROOT. I would call this the most likely thing for
another reviewer to get wrong, and it is only correct because the test measures
liveness rather than the absence of an error.

Scope discipline: I did not touch a single shipped migration, and the allowlist
comment says why. I did not add a CI job. I did not change any migration, role,
or application code. The static audit is wired to nothing, and the README says
so in the same words the index.ts comment uses.

Judgement calls, stated rather than buried:

  - "Reuse the attack-kit CI step's cluster if one already exists; don't add a
    second 10-minute job." The attack-kit lane does not in fact keep a cluster
    alive across steps — it runs pnpm run test:attack-kit, which builds and
    tears down per test. So there was no cluster to reuse. The gate therefore
    builds its own disposable cluster in the same LANE, which satisfies the
    intent (no second job, PostgreSQL 17 already installed, seconds not
    minutes) without pretending a reuse happened. If a shared long-lived
    cluster is wanted later, the --host path is already there for it.

  - I kept the text audit rather than deleting it. It is a genuine convenience
    while writing a migration, and the brief allowed either. It is labelled a
    hint in three places and wired to nothing, and the gate does not consult it.

Limits I want on the record. The gate covers what the migrations PRODUCE. It
does not cover a privileged routine created outside the migration ledger, at
runtime, or by an extension in an app schema — a routine created by
CREATE EXTENSION into an app schema would be audited (it is in pg_proc) but not
necessarily attributable. Extensions install into their own schema, and the
audit's unclassified-schema check is what would catch a surprise there. The
attribution of the 23 shipped violations to issue 421 is inherited from the
previous rounds; I regenerated the allowlist from the real catalog rather than
editing it by hand, so the entries are correct, but I did not re-audit whether
issue 421 is still the right tracking issue for each routine. The 180-day
horizon and the bare-pg_temp strictness are both deliberate; the latter is
strict on a value the catalog can never produce, which is why it is safe.
