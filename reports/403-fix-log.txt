1. WHAT I CHANGED AND WHY
-------------------------

F1 — HIGH, pool self-deadlock.  FIXED.
  The activity service held one pooled connection for its authority
  transaction and then needed a second to read events. The web pool has 8
  connections, so 8 concurrent timeline reads each waited for a slot the
  others held: every request failed at ~5005 ms and the bounded database then
  quarantined itself, so every later query in the whole process returned
  database_unavailable. With EventSource retrying every second, ~8 open
  activity tabs could brick every page until a restart.

  Fixed by reading events on the authority transaction's own connection.
  ProjectEventReadSourceV1.read now takes an optional session; the service
  passes its authority transaction's tx; the store runs the entire read on
  that one connection.
    src/project-events/v1/types.ts:79-88        optional session on the contract
    src/web/v1/project-activity-service.ts:31   passes the authority tx
    src/project-events/v1/store.ts:115-134      one connection, one snapshot

  I considered authorising in a short transaction and then reading on a fresh
  one, and rejected it: that leaves a window in which a committed revocation
  would be read as still-authorised. Raising the pool size only moves the
  cliff, and 8 is the bounded database's design point.

  The brief named private-task-application.ts:60 and mac-local-task-application.ts:88.
  Those are the CONSTRUCTION sites for the read source; the deadlock was in the
  CALL, so those two files needed no edit. I verified by grepping every
  construction and call site that the service is the only consumer reaching
  the store.

F2 — MEDIUM-HIGH, spurious integrity_failed.  FIXED.
  The store read the head row and the event rows in two separate autocommit
  statements, so an append committing in between tripped the final-head
  equality check. About half of all reads failed with a 503 while events were
  being written.
    src/project-events/v1/store.ts:120-124      one REPEATABLE READ READ ONLY tx
  Rejected retrying on integrity_failed: that would mask a genuinely tampered
  head forever and turn a deterministic refusal into a latency-dependent one.

F3 — MEDIUM, stream frozen on "Reconnecting".  FIXED.
    private-app/app/project-activity-timeline.tsx:110-125   onerror branches on
                                                            readyState
    private-app/app/project-activity-timeline.tsx:66-108   bounded backoff + probe
    private-app/app/project-activity-timeline.tsx:52-64    retry-schedule seam
    private-app/app/project-activity-timeline.tsx:29-31    retry countdown copy
    private-app/app/project-activity-timeline.tsx:161-165  401 goes to sign-in
  A non-200 stream response makes the browser close the EventSource permanently;
  the old code only closed its own source after three errors, so the page sat on
  "Reconnecting" forever with no updates and no recovery control. Now:
    readyState 0 (CONNECTING) -> the browser is already retrying; show
      "Reconnecting" and do not add a second competing retry.
    readyState 2 (CLOSED) -> terminal. Bounded backoff (1s, 2s, 4s, 8s, 15s)
      with a visible countdown, then one re-probe of /activity to learn the real
      status, because an EventSource error carries no HTTP status. A 401 becomes
      the sign-in state; a 503 becomes unavailable with "Check saved activity
      again". Events already on screen are never discarded across a retry.
